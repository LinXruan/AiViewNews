# PLAN 11 — 大模型鲁棒性与上下文预算

日期：2026-11-17　｜　阶段：M2（与 PLAN_5 同时落地）

## 1. 为什么单列一份

整条链路里只有模型是不可控的：同样的输入，输出可能带代码块、字段漂移、引用编造、甚至被 `max_tokens` 截断。这一份把"格式不对怎么办"和"上下文怎么管"写成可执行规则，而不是靠现场运气。

## 2. 调用形态：无状态单轮

每次调用只有两条消息（system + user），**不携带任何历史**。跨块、跨任务的信息全部由后端在数据库里拼装，不依赖模型记忆。

理由：多轮会把无关历史越堆越多，成本线性上涨、结果不可复现，且失败后无法只重试出错的那一段。无状态单轮天然支持"重试就是重发"。

**澄清一个前提**：上传 PDF 本身**不调用模型**，只触发 mineru 解析（PLAN_4）；模型调用发生在**查询**时（PLAN_5）。所以同一份 PDF 被查询十次，解析只做一次，十次分析互相独立——上下文在结构上就不可能累积。

三次独立调用：**抽取 → 时间线摘要 → 报告**。各自校验、各自重试，一个失败不连坐。不合并成一次，是因为合并后输出体积大、截断风险高，且失败只能全部重来。

## 3. 上下文预算

| 预算项 | 上限 | 做法 |
| --- | --- | --- |
| 单块输入 | 6000 字符 | chunker 按标题切，超长段落 200 字重叠滑窗 |
| system 提示 | ≤800 字 | 固定模板 + 一个最小 JSON 示例，不贴完整 JSON Schema |
| 单任务调用次数 | `8 × 文档数`，封顶 60 | 超出则剩余块标记 `skipped`、任务 `partial`，并提示"文档过多，建议逐个查询"。固定 40 在多文档任务里会误杀——5 个文档 × 6 块就已经 30 次 |
| 报告输入事件 | ≤20 条 | 超 40 条时按时间均匀抽样 + 首次出现优先压到 20 条 |
| 单块超时 | 60s | 超时按失败重试计 |
| 单任务总时长 | 10min | 超时置 `failed` 并写明卡在哪一步 |

- **不引入 tokenizer 依赖**：中文 1 字约 1 token 量级，6000 字符远低于 64K 窗口，按字符数保守估算足够。
- **最大的省钱点**：`full.md` 解析一次、多查询复用（PLAN_4）。否则每次查询都重跑 mineru，时间和内存都扛不住。

## 4. 格式失败的五层防御

| 层 | 做什么 | 失败后 |
| --- | --- | --- |
| L0 约束 | `response_format=json_object`；prompt 里出现 "json" 字样并给最小示例；`temperature=0.2`；`max_tokens=4096`；**`finish_reason=='length'` 直接视为失败**（截断的 JSON 必然不合法，早点识别别浪费时间解析） | 进 L3 |
| L1 解析 | 剥 ` ```json ` 包裹；截取首个 `{` 到最后一个 `}`；去 BOM、尾逗号、全角引号；`json.loads(strict=False)` | 进 L3 |
| L2 校验 | pydantic 校验 + 字段级归一化：`"第3页"→3`、`"2024年3月5日"→2024-03-05`、`"2024-03"→2024-03-01`、未知字段忽略 | **只重试不合格的条目**，合格条目先收下 |
| L3 局部重试 | 把错误摘要 + 原文回灌（"第 2 条缺 event_time，只返回修正后的完整 JSON"）；第二次把温度降到 0；最多 2 次 | 进 L4 |
| L4 降级 | 单块失败 → 跳过并计数，任务继续；**所有块都失败**才置 `failed`；事件数为 0 → `done` + `no_events` 提示前端换查询词 | 结束 |

关键点：**局部成功要保住**。8 条里 6 条合格，重试的是那 2 条，不是整块重来；否则一次小漂移就把整块结果扔掉，成本和体验双输。

**截断类失败是例外**：`finish_reason=length` 说明块本身太大，原样重试还会截断。这类失败重试时先把该块**折半**再送，不要照原样重发——这是唯一需要改输入而非重试的重试。

## 5. 幻觉引用：定成硬规则

`source_quote` 在 `full.md` 里搜不到时，先用归一化文本（去空白、统一全半角标点）再搜一次；**仍然找不到就丢弃这条事件**，并计数写进任务统计。

理由：编造的引用比少一条事件严重得多。时间线的可信度是评分核心，老师很可能现场点开一条事件去核对原文——点开发现原文里没有这句话，比少一条事件难解释。

实现要点：归一化时同步维护"归一化字符串索引 → 原文字符偏移"的映射数组，`find` 命中后回查映射得到真实偏移。

## 6. 可观测性：日志而非建表

每次调用追加一行到 `data/logs/llm.jsonl`：`task_id, chunk, attempt, model, prompt_chars, output_chars, latency_ms, finish_reason, ok, error`。

不建 `llm_calls` 表：热路径多一次写库没必要，日志足以排查问题；技术报告要的"调用次数 / 平均耗时 / 失败率"从日志聚合即可。

## 7. 幂等与重入

- 任务重跑前先 `DELETE FROM events WHERE task_id=?`，避免叠加重复事件。
- 进程重启把 `analyzing` 重置为 `pending` 后，若该任务已有部分事件落库，重跑时同样先清空。
- 同一查询重复建任务不冲突：每个任务的 `events` 按 `task_id` 隔离。

## 8. 验证（必须逐条造出来）

1. 返回被 `max_tokens` 截断（`finish_reason=length`）→ 重试后成功，不是解析报错。
2. 返回裹了 ` ```json ` 和前后寒暄 → 正常解析。
3. 8 条事件里有 2 条缺字段 → 6 条入库，仅 2 条触发重试。
4. `page` 返回 `"第3页"`、`event_time` 返回 `"2024年3月5日"` → 正常归一化入库。
5. 整块与查询无关返回 `[]` → 任务 `done`，不报错。
6. 伪造 `source_quote`（原文没有）→ 该条被丢弃，其余保留，统计里有计数。
7. 模拟 429 → 指数退避后重试成功。
8. 断网 → 3 次尝试后任务 `failed`，`error` 可读，前端有明确提示。

## 9. 回退

删掉 L1–L3 与归一化逻辑，退化为"解析失败即任务失败"。功能仍能演示，但一次格式漂移就中断，只作为答辩前的应急开关。
